# ADR-018 · 2026-04-30 · Agent Client Protocol (ACP) alignment + typed action enum (Warp + Zed-derived)

**Decision.** Hivecore agents speak Agent Client Protocol natively in Layer 2 via a `hivecore-acp` crate. The crate maps hivecore's internal `AgentEvent` and tool-call surfaces onto ACP messages so any ACP client (Zed, future IDEs) can mount a hivecore agent process unmodified. Internally, agent-side actions are modeled as a single typed enum (`HivecoreAction`) paired with a result enum (`HivecoreActionResult`), following Warp's `AIAgentActionType`/`AIAgentActionResultType` shape. Each action variant carries risk metadata (`is_read_only: Option<bool>`, `is_risky: Option<bool>`, `wait_until_completion: bool`, `rationale: Option<String>`, `citations: Vec<Citation>`). Variants include the standard set (Bash, ReadFiles, Grep, Edit, FileGlob, MCPTool, MCPResource) plus harness-pluggability variants (`StartAgent { harness_type, persona_id, tenant_id, model_id, ... }`, `SendMessageToAgent`, `AskUserQuestion`, `TransferShellCommandControlToUser`).

**Context.** Zed's `crates/agent_servers` + `crates/acp_thread` already mount external agents (Claude Code, Codex, opencode) via ACP — speaking ACP gets hivecore free distribution into Zed and future ACP-aware tools without per-IDE adapters. Warp's action enum is the cleanest typed action protocol seen in the prior art: every agent capability is a variant, every result a paired variant, risk metadata baked in. Combining the two — ACP as wire format for editor↔agent, Warp-style action enum as internal request shape — gives hivecore both interop and a clean type system.

**Alternatives considered.**
- **Custom hivecore RPC, no ACP.** Maximum design freedom, zero free distribution. Rejected — ACP alignment is a strategic distribution win.
- **ACP only, no internal action enum.** Couples internal types to wire format; harder to evolve. Rejected.
- **MCP everywhere, no ACP.** MCP is for tools, not for agent↔editor session protocol. Different layer.
- **Implement only a subset of ACP.** Acceptable v0.1 scope; commit to full ACP by v0.5.

**Consequences.**
- v0.1 includes a `hivecore-acp` crate with ACP server impl + minimal action enum (8–10 variants).
- Action variants are extension-extensible: extensions register new action types via WIT; host marshals to ACP `tool` calls.
- Risk metadata enables Layer 3 gates (UOK Gate Plane) to make typed decisions: `is_risky=true` → user confirmation required; `is_read_only=true` → safe in dry-run mode.
- `StartAgent { harness_type, persona_id, tenant_id }` is the multi-agent orchestration entry point — directly validates hivecore's pluggable-harness thesis (Warp's design proved it works).
- Cost: ACP is a moving spec — couple loosely, version-pin, expect periodic upgrades.

**Revisit when.** ACP fragments (multiple incompatible forks emerge), or a clearly superior agent protocol gains adoption (e.g., MCP-Agent, or OpenAI Assistants protocol matures into a real standard).
