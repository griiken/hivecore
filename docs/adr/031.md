# ADR-031 · 2026-05-04 · `ExecutionEnv` trait — pluggable I/O for builtin tools

**Decision.** Introduce `ExecutionEnv` as a Layer-1 trait in `hivecore-runtime-core`. Every builtin tool that touches the filesystem or spawns processes (`bash`, `read_file`, `write_file`, `edit_file`, `grep`) takes an `Arc<dyn ExecutionEnv>` instead of calling `tokio::process::Command` / `std::fs` / `tokio::fs` directly. Default impl `LocalEnv` ships in the same crate (or a sibling `hivecore-execution-env` crate if `runtime-core` must stay zero-I/O — TBD during implementation; the trait surface is identical either way).

**Trait surface (locked here):**

```rust
// hivecore-runtime-core/src/execution_env.rs

#[derive(Debug, Default, Clone)]
pub struct ExecOpts {
    pub cwd: Option<PathBuf>,
    pub env: BTreeMap<String, String>,
    pub timeout: Option<Duration>,
    pub signal: Option<AbortSignal>,
}

#[derive(Debug, Clone)]
pub struct ExecOutput {
    pub stdout: Vec<u8>,
    pub stderr: Vec<u8>,
    pub exit_code: i32,
}

#[derive(Debug, Clone)]
pub struct FileStat {
    pub is_file: bool,
    pub is_dir: bool,
    pub is_symlink: bool,
    pub size: u64,
    pub mtime: SystemTime,
}

#[derive(Debug, Default, Clone)]
pub struct RemoveOpts {
    pub recursive: bool,
    pub force: bool,
}

#[async_trait]
pub trait ExecutionEnv: Send + Sync + Debug {
    fn cwd(&self) -> &Path;

    async fn exec(&self, command: &str, opts: ExecOpts) -> RuntimeResult<ExecOutput>;

    async fn read_file(&self, path: &Path) -> RuntimeResult<Vec<u8>>;
    async fn read_text_file(&self, path: &Path) -> RuntimeResult<String>;
    async fn write_file(&self, path: &Path, bytes: &[u8]) -> RuntimeResult<()>;
    async fn stat(&self, path: &Path) -> RuntimeResult<FileStat>;
    async fn list_dir(&self, path: &Path) -> RuntimeResult<Vec<PathBuf>>;
    async fn path_exists(&self, path: &Path) -> RuntimeResult<bool>;
    async fn create_dir(&self, path: &Path, recursive: bool) -> RuntimeResult<()>;
    async fn remove(&self, path: &Path, opts: RemoveOpts) -> RuntimeResult<()>;

    async fn create_temp_dir(&self, prefix: Option<&str>) -> RuntimeResult<PathBuf>;
    async fn create_temp_file(&self, prefix: Option<&str>, suffix: Option<&str>)
        -> RuntimeResult<PathBuf>;

    fn resolve_path(&self, path: &Path) -> PathBuf;

    /// Best-effort cleanup on drop / shutdown. Idempotent.
    async fn cleanup(&self) -> RuntimeResult<()>;
}
```

**Context.** All v0.1 builtin tools call OS APIs directly:

- `crates/hivecore-builtin-tools/src/bash.rs:78-86` — `tokio::process::Command::new("bash")`.
- `crates/hivecore-builtin-tools/src/read.rs` / `write.rs` / `edit.rs` — `tokio::fs` directly.
- `crates/hivecore-builtin-tools/src/grep.rs` — `tokio::process::Command::new("rg")` / `grep`.

This blocks every interesting deployment target: Firecracker microVMs (P3 sandbox crate), Docker containers, remote SSH boxes, leased cloud runners (per ADR-019 sandbox plane goals). Today retrofitting any of those means rewriting all five tools each time. The browser harness (ADR-028) already faced this and solved it with `BrowserProvider` — same pattern, scoped to browser. `ExecutionEnv` generalises that pattern to fs+process I/O.

The trait must be Layer-1 (in `runtime-core`) for two reasons:

1. Tools are Layer-3 but consume the trait by reference; the trait itself is a contract, not an implementation, and contracts live in `runtime-core` per ADR-016.
2. Future work (ADR-019 sandbox plane, P3 Firecracker runner, P5 Daytona/e2b connectors) needs to depend on the trait without a circular crate dep on builtin-tools.

If keeping `runtime-core` strictly zero-I/O matters more than crate count, the `LocalEnv` impl moves into a sibling `hivecore-execution-env` crate. The trait shape doesn't change.

**Alternatives considered.**

1. **Keep direct OS calls in tools, add a "sandbox wrapper tool" hook later.** Rejected. Wrapping at the hook level can intercept exec but not fs reads/writes (those happen inside tool bodies before any hook fires). And every new sandbox provider would still need per-tool patches.
2. **One trait per concern (`Filesystem` + `Processes` + `Tempfiles` separate).** Rejected. Sandbox providers conceptually own all three at once — leasing a Firecracker VM gets you fs + exec + temp atomically. Splitting forces every impl to coordinate three traits, and tools to take three Arcs.
3. **Make `ExecutionEnv` an associated type on `Tool`.** Rejected. Tools must be heterogeneously dispatched (`Vec<Arc<dyn Tool>>`), so they can't have unbounded associated types. Trait-object `Arc<dyn ExecutionEnv>` plumbed through tool constructors is the only shape that composes.
4. **Embed sandbox choice in `WorkspaceRoot`.** Rejected. `WorkspaceRoot` is a path-validation primitive (`safety.rs`); conflating it with I/O dispatch couples concerns and breaks defence-in-depth. `WorkspaceRoot` continues to own path validation; `ExecutionEnv` owns I/O execution.
5. **Defer until P3 sandbox crate.** Rejected. Tools shipping more functionality without the trait means more surface to refactor later. Cheaper to land the trait now and retrofit five tools than to retrofit five tools plus future additions.

**Wiring plan.**

| Crate | Change |
|---|---|
| `hivecore-runtime-core` | New module `execution_env.rs`; trait + value types + `LocalEnv` (or punt `LocalEnv` to sibling crate per Context above). |
| `hivecore-builtin-tools` | Each tool gains `env: Arc<dyn ExecutionEnv>` field. Constructors take it. `WorkspaceRoot` stays for path validation. `bash.rs` calls `env.exec(...)` instead of `Command::new`. `read.rs` / `write.rs` / `edit.rs` call `env.read_file` / `write_file`. `grep.rs` calls `env.exec("rg ...")`. |
| `hivecore-coder` | Wires `LocalEnv::new(workspace_root)` once, passes `Arc::clone` to each tool. |
| `hivecore-acp-server` | Same wiring as `hivecore-coder`. |
| `hivecore-browser-runtime` | No change. `BrowserProvider` is a parallel abstraction, scoped to browser DOM/CDP. `ExecutionEnv` is fs+process. They coexist. |

**Consequences.**

*Enables.*
- Future Firecracker / Docker / remote / leased-runner sandboxes drop in as `ExecutionEnv` impls without touching any tool.
- ADR-019 sandbox plane has its substrate.
- Tests can use a `MemoryEnv` (in-memory fs, scripted exec) — faster + hermetic than spawning real shells.
- Multi-tenant deployments can give each session its own env (Firecracker microVM per session), enforced at trait-boundary, not by trusting tool authors.
- Tool authors have one I/O surface to review, not five flavours of `tokio::*`.

*Costs.*
- ~400 LOC: trait + types (~120) + `LocalEnv` impl (~200) + tool retrofit (~80 across 5 tools).
- One new field per builtin tool struct. Constructor change is a breaking API for downstream tool consumers — pre-1.0, acceptable, called out in CHANGELOG.
- Slight indirection cost on the hot path (`Arc<dyn>::exec` vs direct `Command::new`). Trivial vs the LLM round-trip dominating turn latency.

**Revisit when.**
- A second `ExecutionEnv` impl ships and reveals an awkward method (e.g., `create_temp_file` proves provider-incompatible) — refine the trait then.
- Streaming exec output (per-chunk callbacks) becomes load-bearing — currently `ExecOpts` has no `on_stdout` callback; tools rely on the existing `UpdateSink` for partial UI updates. If a sandbox provider can only stream, add `on_stdout`/`on_stderr` to `ExecOpts`.
- Cross-platform path conventions (Windows separators) cause divergence between `LocalEnv` and a remote `ExecutionEnv` — formalise via `resolve_path`.
- Tool-policy (ADR-029) gains an inspector that needs to peek at the env's identity (which sandbox? which tenant?) — add a `EnvInfo` accessor on the trait.
