# ADR-022 · 2026-04-30 · Lifecycle hooks vs tool hooks — separate trait, same trichotomy

**Decision.** Hivecore exposes **two** hook trait surfaces:

- `ToolHook` — gates *tool* calls. Outcome: `Pass | Override | FailedContinue | FailedAbort | ManualAttention`. Extra `Override` variant lets a hook substitute a synthetic tool result.
- `LifecycleHook` — gates *non-tool* checkpoints (agent start/end, turn boundaries, pre-model-request, post-message-commit). Outcome: `Pass | FailedContinue | FailedAbort | ManualAttention`. No `Override` (lifecycle events have no result to substitute).

The driver fires both at the appropriate points. A `FailedAbort` from either short-circuits with `LoopError::HookAborted(reason)`. `ManualAttention` short-circuits with `LoopError::ManualAttention(reason)`.

**Context.** Codex's `HookFn` (in `hook_runtime.rs`) uses one type with a `HookEvent` discriminant. pi-mono uses shell-cmd JSON over stdin/stdout per event. Claude Code uses script files in `.claude/hooks/` keyed by event name. All three converge on the same trichotomy of outcomes.

We could have done one trait with one large event enum. Splitting tool-vs-lifecycle keeps each trait's outcome enum semantically clean (the `Override` variant only makes sense for tool calls) and lets implementors handle a subset of events without a giant `match` for every variant.

**Alternatives considered.**
- **One unified `Hook` trait with one `HookEvent` enum.** Saves a trait. Forces a `match` over many variants. Forces the outcome enum to carry an `Override` variant that's invalid for most events. Rejected.
- **Separate trait per event class (PreModelHook, PostTurnHook, etc.).** Eight traits. Composability via dyn-dispatch becomes brittle. Rejected.
- **Generics — `Hook<E: HookEvent>`.** Trait objects must erase the type parameter. Defeats the purpose of trait-object composability. Rejected.

**Consequences.**
- Two trait imports (`ToolHook`, `LifecycleHook`). Cost is one extra `use` line per implementor.
- Documenting "which hook do I implement?" becomes the doc comment's job. Default mental model: "if you mutate a tool result, it's a `ToolHook`; otherwise it's a `LifecycleHook`."
- Both traits can co-exist on the same struct — a security plugin that wants to gate both shell commands and pre-model-requests just impls both.

**Revisit when.** A third hook surface emerges (e.g. KG-write hooks, audit-emit hooks) and the trio still maps cleanly to typed outcomes. If an enum-of-enums explosion starts to bite, revisit unification.
