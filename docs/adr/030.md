# ADR-030 · 2026-05-03 · Switch to Apache-2.0-only licensing (supersedes ADR-002)

**Decision.** Hivecore is licensed solely under the **Apache License, Version 2.0** going forward. The dual MIT-OR-Apache-2.0 choice from ADR-002 is superseded as of this commit. Single root `LICENSE` file (full Apache-2.0 text). `LICENSE-MIT` deleted; `LICENSE-APACHE` content moved into `LICENSE` and the duplicate `LICENSE-APACHE` file deleted.

Workspace `Cargo.toml` updated: `license = "Apache-2.0"`. README, AGENTS.md, docs/terms.md updated. CHANGELOG entry under [Unreleased].

**Context.** ADR-002 (2026-04-29) chose dual MIT-OR-Apache-2.0 to follow Rust ecosystem convention (rustc / tokio / serde / etc.). After v0.1 substrate landed on 2026-05-03, the dual licence created friction:

- Three files at the repo root (`LICENSE` as dual-pointer, `LICENSE-MIT`, `LICENSE-APACHE`) confused tooling and contributors. GitHub's licence detector flagged the repo as "Other" until disambiguated.
- The `LICENSE-MIT` arm offers no patent grant, while every vendored upstream prompt under `crates/hivecore-system-prompt/prompts/` (Codex, Zed) is Apache-2.0 only. Mixing creates a strict-Apache subset that downstream consumers had to track manually.
- ADR-007 commits hivecore to a CONFIG-not-code substrate where org-customised harnesses include the licence text in their own distributions; one licence file ships cleaner than three.
- Apache-2.0 §5 already covers inbound contributions; the dual-licence "you grant both" wording in `docs/terms.md` was redundant and CLA-shaped without the CLA.

**Alternatives considered.**

1. **Keep dual MIT-OR-Apache-2.0 (ADR-002 status quo).** Rejected — the friction above is real and the "matches Rust ecosystem convention" argument is weakening (newer Rust projects increasingly pick a single licence — Apache-2.0 or MPL-2.0 are both common). One-file simplicity wins.
2. **Switch to MIT-only.** Rejected — gives up the explicit patent grant, which v0.1 specifically wants for vendored prompt safety + downstream contributor protection.
3. **Switch to MPL-2.0.** Considered — file-level copyleft would protect community modifications. Rejected: too restrictive for a substrate intended to be embedded in proprietary harnesses (per ADR-007 — orgs configure their own harnesses on top of hivecore).
4. **Switch to AGPL-3.0.** Rejected on the same ground as MPL — kills commercial adoption of the substrate.
5. **Switch to BSL with eventual Apache-2.0 conversion.** Rejected — adds vendor-control optics that contradict hivecore's "OSS substrate" positioning. Apache-2.0 is the cleanest "permissive with patent grant" option.

**Consequences.**

*Enables.*
- Single licence file at root — GitHub licence detector picks Apache-2.0 cleanly; packagers (crates.io, npm-side later) read `Cargo.toml`/`package.json` `license` field unambiguously.
- All vendored prompts (Apache-2.0) and project code now under one licence — no compatibility matrix.
- `docs/terms.md` simplifies to one inbound-contribution clause grounded in Apache-2.0 §5 — no CLA needed.

*Costs.*
- **Anyone who pulled the tree at a commit before this ADR retains MIT terms forever for that snapshot.** Cannot be retroactively revoked. Going-forward consumers see Apache-2.0 only.
- Existing forks tagged before this ADR may continue under either licence at their option per ADR-002. They are not bound by this change.
- Loss of the bare-MIT path for downstream consumers who specifically wanted to avoid Apache-2.0's notice-preservation requirements (NOTICE file, modification tracking). Hivecore deems this an acceptable cost.
- ADR-002 stays in the log (append-only — never deleted) and links forward to this ADR via the `supersedes` linkage in the index.

**Revisit when.**
- A jurisdiction adopts patent-grant law that makes Apache-2.0's §3 redundant or harmful (unlikely).
- Hivecore commercial offering structure changes such that BSL or AGPL-style restrictions become useful (e.g., source-available with eventual Apache conversion).
- Major dependency adopts a non-Apache-compatible copyleft licence and forces a re-evaluation.
