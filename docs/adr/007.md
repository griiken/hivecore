# ADR-007 · 2026-04-29 · Personas, workflows, and policies are CONFIG, not code

**Decision.** Persona definitions, workflow DAGs, and control-plane policies live in TOML files under `.hivecore/`. They are parsed by `crates/hivecore-config` at runtime. Org customization happens in config, not in source.

**Context.** The unique wedge of hivecore versus competitors (multica, paperclip, ai-sdlc-framework, BMad, Spec-Kit, Kiro) is that every other platform hardcodes some combination of persona, workflow, or governance. Hivecore makes all three customizable per-org without forking source.

**Alternatives considered.**
- **Code-only personas** — flexibility lost, every customization is a fork.
- **DSL-only personas** — adds learning curve and parser complexity.
- **YAML configs** — fine, but TOML is more typed and Rust-ecosystem-native.

**Consequences.** Forces a stable, extensible config schema (versioned, with migration support). Schema changes need ADRs. Validation is rigorous (parser rejects malformed configs at boot, not at runtime). Orgs can ship their hivecore harness as a config bundle, no code changes.

**Revisit when.** Config schema collapses under feature pressure, or a sufficiently expressive DSL would simplify common patterns.
