# ADR-017 · 2026-04-30 · Extension boundary = WASM Component Model + WIT (Zed-derived)

**Decision.** Hivecore extensions are compiled to WebAssembly Component Model components. The host↔extension contract is defined by versioned WIT files in `crates/hivecore-extension-api/wit/since_vX.Y.Z/`. Each extension ships an `extension.toml` manifest at its root declaring `id`, `name`, `version`, `schema_version`, `provides` (capabilities allowlist), `tenancy` (single|multi), and `permissions` (declared tool names + filesystem globs + network hosts). The `hivecore-extension-host` crate runs extensions in a sandboxed WASM runtime (wasmtime). Hot-reload supported via `/reload`; install-time precompilation default.

Manifest is mandatory and validated against a JSON schema in `hivecore-config`. An extension cannot register tools, providers, or subscriptions outside its declared `provides`/`permissions` — host enforces.

**Context.** pi-mono's extension model loads TypeScript via `jiti` at startup — convenient, but extensions execute with full Node permissions (the docs explicitly warn about it). Zed solves the same problem with WASM Component Model + a versioned WIT API: extensions are sandboxed by construction, the API is forward-compatible across versions (`since_v0.0.1` … `since_v0.8.0`), and the manifest declares capabilities up front. Hivecore is multi-tenant; we cannot run untrusted org-supplied extension code with host-process permissions. WASM gives us the sandbox; WIT gives us a stable, language-neutral API; the manifest gives us tenancy + permission declarations the host can check before granting any tool registration.

**Alternatives considered.**
- **TypeScript via jiti (pi-mono pattern).** Fast iteration, weak isolation. Rejected — multi-tenant + untrusted-extension goal forces sandboxing.
- **`dlopen` of Rust cdylibs.** Native speed but no sandbox; ABI fragility across compiler versions. Rejected.
- **Subprocess + JSON-RPC per extension.** Strong isolation but high overhead and complex lifecycle. Reserve for "heavy" extensions (LSPs, browsers); not the default.
- **Lua/JS scripting embedded in host.** Familiar but reinvents the sandbox; weaker than WASM for arbitrary languages.
- **WASI Preview 1 instead of Component Model.** Older, less expressive types, no resource handles. Rejected — Component Model is where the ecosystem is going.

**Consequences.**
- Extension authors compile to WASM (Rust, Go, JS via componentize-js, Python via componentize-py).
- Host (`hivecore-extension-host`) embeds wasmtime. Wasmtime becomes a transitive dep — vet license/binary-size impact in Phase 1.
- WIT versioning discipline required: every breaking change → new `since_vX.Y.Z` directory; old versions kept compiled for compatibility.
- Manifest-declared permissions enable static auditability without running the extension.
- Cost: slower iteration than TS hot-reload (compile step); larger binary footprint (wasmtime ≈ 5–10 MB).
- Layer boundary: WIT lives in Layer 2 (`hivecore-extension-api`), host in Layer 2 (`hivecore-extension-host`). Layer 1 is unaware of extensions.

**Revisit when.** Wasmtime stalls or a competing Component Model runtime materially outpaces it; WIT 2.0 introduces breaking changes; or extension authoring friction blocks adoption (then add a higher-level scripting layer on top, do not abandon WASM).
