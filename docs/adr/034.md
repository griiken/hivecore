# ADR-034 · 2026-05-04 · Parallel tool dispatch with per-tool execution mode

**Decision.** `hivecore-agent-loop` dispatches the tool calls of a single assistant message in **parallel by default**, with a per-`Tool` opt-out. A new method `Tool::execution_mode() -> ToolExecutionMode` defaults to `Parallel`. Tools that mutate workspace state (`write_file`, `edit_file`, `bash`) override to `Sequential`. The driver groups calls by mode: parallel-eligible calls run concurrently via `futures::future::join_all`; sequential calls run one-at-a-time, in assistant-message-source order, after the parallel batch settles. Tool-result message artifacts are emitted in assistant source order (preserved for reproducibility), but `tool_execution_end` events fire in completion order so the UI can show results as they arrive.

```rust
// hivecore-runtime-core/src/tool.rs
#[derive(Debug, Clone, Copy, PartialEq, Eq)]
pub enum ToolExecutionMode {
    Sequential,
    Parallel,
}

#[async_trait]
pub trait Tool: Send + Sync + Debug {
    // ... existing methods unchanged ...

    /// Hint for the agent loop. Default: Parallel.
    /// Override Sequential for tools that mutate shared state where
    /// concurrent calls would cause races (writes, edits, exec).
    fn execution_mode(&self) -> ToolExecutionMode {
        ToolExecutionMode::Parallel
    }
}
```

**Default settings (locked):**

| Tool | Mode |
|---|---|
| `read_file` | Parallel |
| `grep` | Parallel |
| `list_dir` | Parallel |
| `write_file` | Sequential |
| `edit_file` | Sequential |
| `bash` | Sequential |
| MCP meta-tools (`mcp_servers`, `mcp_discover`) | Parallel |
| MCP `mcp_call` | Sequential (conservative; MCP-side `read_only_hint` ⇒ Parallel — handled in v0.2 by `RiskAugmenter`-driven mode resolution) |
| Browser tools (`browser_*`) | Sequential |
| `SpawnAgentTool` | Sequential |

**Context.** Today's driver loops `for call in calls` and awaits each tool serially (`crates/hivecore-agent-loop/src/driver.rs:325`). A turn that fires four `read_file` calls pays four full round-trips of latency. The model has no visibility into ordering and assumes parallel execution where calls are independent. Real-world coding sessions routinely fire 3-8 read/grep tools per turn — this is on the hot path of every task.

The hook surface (`ToolHook::before` / `after`) is *per-invocation*, not per-batch, and stays per-invocation under parallel dispatch. The `ApprovalHook` (ADR-029) already handles concurrent prompts via session-cache and the existing `Approval` async trait — no contention; multiple `Approval::request` calls can be in-flight.

**Alternatives considered.**

1. **Always sequential.** Status quo. Rejected — measurable latency cost, ergonomic mismatch with how models think about tool batches.
2. **Always parallel.** Rejected — `bash` running two `git checkout` commands concurrently would corrupt the workspace. Sequential-by-default for state mutators is non-negotiable; the per-tool flag is the right granularity.
3. **`AgentLoopBuilder::tool_execution(Sequential | Parallel)` global.** Rejected on the same grounds as (2). Per-tool is the correct axis.
4. **Group by hook tag (e.g., "read-only" hooks ⇒ parallel).** Rejected — hooks are orthogonal to tools; a read-only hook applied to `edit_file` shouldn't unlock parallelism. The decision belongs on the tool, not on the hook.
5. **Defer until a perf measurement campaign.** Rejected — the win is obvious (every turn with ≥2 read tools), the cost is bounded (~150 LOC), and the API delta is one default-method addition that's strictly additive for existing `Tool` impls.

**Wiring.**

| Crate | Change |
|---|---|
| `hivecore-runtime-core` | Add `ToolExecutionMode` enum + default method on `Tool`. |
| `hivecore-agent-loop` | `dispatch_tools` partitions `calls` by `tool.execution_mode()`. Parallel batch via `join_all` (preserving cancellation through `AbortSignal`). Sequential batch in source order after parallel completes. Result vec re-sorted to source order before emitting `Custom { kind: "tool_result" }` messages. `AgentEvent::ToolExecEnd` fires in completion order during the batch. |
| `hivecore-builtin-tools` | `bash`, `write`, `edit` override to `Sequential`. `read`, `grep`, `list_dir` keep default (`Parallel`). |
| `hivecore-mcp-client` | `mcp_call` overrides to `Sequential` for v0.1 (conservative). Tracked: v0.2 reads `RiskHint.read_only` per invocation, dispatches accordingly. |
| `hivecore-browser-harness` | All `browser_*` tools override to `Sequential` (single shared browser session). |

**Cancellation semantics.** `AbortSignal` is shared across all tools in a batch. A cancel propagates to every in-flight parallel call simultaneously and to the next sequential call before it starts. Already-completed calls keep their results in the batch payload.

**Consequences.**

*Enables.*
- Multi-read / multi-grep turns finish in ~max(latency) instead of ~sum(latency). Common case: 4 reads at ~50ms each → 50ms instead of 200ms.
- Composable: a future custom tool author opts in by default, opts out explicitly.

*Costs.*
- ~200 LOC in driver.rs (partition + join + reorder).
- ~50 LOC across builtin tools to override defaults.
- Test surface: ~12 new tests (parallel happy path, sequential preservation, mixed batch ordering, cancellation across modes, result-emit-order vs event-emit-order).
- Slightly trickier event timeline for log readers; documented in `EVENTS.md`.

**Revisit when.**
- A `RiskAugmenter` reliably classifies MCP tools as read-only — promote `mcp_call` to dynamic mode resolution.
- Frontend grows a "tool batch view" that wants precise event ordering — confirm `ToolExecEnd` completion order is preserved across crash/replay.
- A tool author needs per-invocation mode (e.g., `bash` is sequential normally but `bash` invoking `cat` is read-only) — extend the trait method to take `&ToolInvocation`.
