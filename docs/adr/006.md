# ADR-006 · 2026-04-29 · KG-at-core (not bolted on)

**Decision.** The knowledge graph is hivecore's spine. Orchestrator state, gate inputs, skill ranking, role context — all are KG queries. KG is not a context-retrieval cache.

**Context.** Multiple converging signals: PlayerZero's world model, Bito's "living graph", Tabnine ECE, Augment Code, Lasnoski's "Enterprise KG for SDLC is the foundation of agentic-first development" thesis. The Code Digital Twin paper (arxiv 2503.07967) formalizes the model. Generic platforms (PlayerZero, Bito) build generic KGs; hivecore's wedge is making the KG schema-extensible (orgs add custom node/edge types) and persona/workflow/policy first-class config.

**Alternatives considered.**
- **RAG-only** — vector store + retrieval, no graph structure. Loses relational reasoning, blast-radius queries, temporal facts.
- **KG as bolt-on** — graph alongside vector store, queried opportunistically. Common but underdelivers; KG never becomes load-bearing.
- **Graph-database-only** — no embeddings, weaker for fuzzy semantic queries.

**Consequences.** Graph is the source of truth; everything else (state, audit, gates) reads/writes it. Higher initial complexity; massive payoff at scale (compounds with more data, supports sim layer in P19). Decision drives substantial engineering investment in `crates/hivecore-kg/`.

**Revisit when.** Graph operations become a perf bottleneck that vector-only could have served, OR a strictly better OSS KG engine emerges that justifies switching.
